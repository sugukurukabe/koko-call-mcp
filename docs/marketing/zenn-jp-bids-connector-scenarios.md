# JP Bids MCP を三つの現場で動かす — 入札×補助金×会計、入札×競合調査、入札×チーム共有

## エラーメッセージは、いつも同じ顔をしていた

「官公需入札検索で一時的なエラーが発生しました。条件を絞って再実行してください。」

JP Bids MCP は、この一文をずっとフォールバックとして返していた。官公需情報ポータルサイト（KKJ / 中小企業庁 官公需情報ポータルサイト）の応答が数秒遅れても、502を返しても、`<Results>` タグを一瞬欠いても、ユーザーが見る文章は同じだった。原因は三つあるのに、表示は一つしかない。

Anthropic のディレクトリに載ってから気づいたのは、載ることと、載ったまま業務で使われ続けることは別の作業だという、当たり前の事実だった。営業担当者が商談前に入札を検索して、そこで意味の取れないエラーに当たれば、その人はもう二度と開かない。

## エラーは隠すのではなく言い分ける

原因は三つに分かれていた。KKJ API のタイムアウト、5xx 系の一時障害、そして XML の `<Error>` タグが返す本当の入力ミス。従来の実装は、この三つを同じ `catch` で受け止め、同じ日本語一文にまとめていた。

直した内容は次の三つです。

| 変更 | 内容 |
|---|---|
| **再試行** | 5xx・タイムアウト・ネットワーク断のみ、指数バックオフで最大2回再試行する。4xxと入力ミス（`<Error>`）は再試行しない |
| **タイムアウト設定** | `JP_BIDS_KKJ_TIMEOUT_MS` 環境変数でタイムアウトを調整可能にし、既定値を10秒から15秒に上げた |
| **エラー文の分離** | タイムアウトには「30秒待って再実行」、5xxには「HTTPステータス付きで一時障害の可能性」、入力ミスには元の具体的な修正案を、それぞれ別の文で返す |

再試行のあいだも、KKJ への短時間大量アクセスを避けるレートリミッタ（既定 1 req/sec）は毎回通す。「直す」ことと「KKJに迷惑をかけない」ことは、この実装では同じ関数の中にある。

知っているだけでは直したことにならない。`vitest` で「502は再試行して成功する」「503を3回返せば諦めて例外を投げる」「404は再試行しない」「KKJの`<Error>`応答は再試行しない」の4パターンをテストに落として、初めて直ったと言える。

## 持ち帰れるようになったもの

検索結果は、会話の中で読むだけのものではない。JP Bids MCP には MCP Apps（対応クライアントの会話内に直接描画される画面）で動く `search_bids_app` があり、そこに今回、次の3つの持ち帰り方を追加した。

| 出力形式 | 用途 | 変更点 |
|---|---|---|
| **CSV** | Excelで一覧管理 | UTF-8 BOMを付与し、日本語の文字化けを解消 |
| **ICS** | Googleカレンダー / Outlookに締切を登録 | 選択中の案件から提出期限・開札日を抜き出し、その場で生成 |
| **Markdown** | 社内共有メモ | 件名・発注機関・日程・公式URL・出典を1枚のメモに整形 |

いずれも `ui/download-file` を使い、ホストがダウンロードを許可しない場合はクリップボードコピーへ自動的に落ちる。落ちた先でクリップボード書き込みが働くように、UIリソースの `_meta.ui.permissions.clipboardWrite` も明示した。これは MCP Apps 仕様が定める「サーバーは自分が必要とする権限を宣言し、ホストがそれを尊重するかを決める」という設計に沿った変更であり、独自のワークアラウンドではない。

## 三つの現場 — 入札検索を起点にした連携

入札検索は、それ単体では終わらない。案件を見つけたあとには「原資はあるか」「相手は実在するか」「誰と共有するか」という問いが続く。JP Bids MCP を他の MCP コネクタと組み合わせると、この続きの問いに一つの会話で答えられる。

| シナリオ | 組み合わせるコネクタ | 想定ユーザー |
|---|---|---|
| 入札 × 補助金 × 会計 | J-Grants MCP + freee MCP | 地方の受託開発会社 |
| 入札 × 競合調査 | 法人番号 MCP（Corporate Number） | 建設・役務系の中小企業 |
| 入札 × チーム共有 | 保存検索 + Googleカレンダー + Slack | 営業3〜5名規模の中小企業 |

### シナリオ1: 入札 × 補助金 × 会計 — 原資を確保してから入札する

デジタル庁の J-Grants MCP（[digital-go-jp/jgrants-mcp-server](https://github.com/digital-go-jp/jgrants-mcp-server)）と freee MCP を JP Bids MCP に並べると、「IT導入補助金で原資を確保した上で、対応するシステム調達案件を絞り込む」という一連の判断を一つの会話で行える。

```
IT補助金で原資を確保した上で、鹿児島県のシステム調達案件を絞り込んでください。
補助金の申請期限と入札の提出期限が重ならない組み合わせを提案してください。
```

この組み合わせの詳細と4つのワークフロー例は、[JP Bids MCP × Jグランツ MCP × freee MCP](../articles/zenn-jp-bids-jgrants.md) にすでに公開している。ここでは三つのうち一つとして位置づけるだけにとどめる。

### シナリオ2: 入札 × 競合調査 — 常連落札者を、取引先候補として照合する

`analyze_past_awards`（過去公告・競合レーダー）は、過去の公告を集計して発注機関の頻度やカテゴリ偏りを返す。地域とキーワードを絞れば、「同じ発注機関から繰り返し案件が出ている業種」が見えてくる。

次に、そこに現れた企業名を、Public MCP JP Gateway 経由の法人番号 MCP（国税庁 法人番号公表サイト Web-API を利用したコネクタ）に渡し、法人番号・本店所在地・履歴を確認する。Gateway の registry には、この組み合わせにそのまま対応する `counterparty_check`（取引先照合）モードが定義されており、`search_corporations` と `get_corporation_by_number` の2ツールだけを見せる。建設・役務系の入札では、単独では参加資格を満たせない案件に共同企業体（JV）で応じることがある。競合として見ていた相手が、実は共同入札のパートナー候補になることもある。

```
鹿児島県の役務入札で、過去1年に繰り返し受注している発注機関と業種を分析してください。
そこに出てきた企業の法人番号と所在地を確認してください。
```

1. `analyze_past_awards(prefecture="鹿児島県", category="役務", window_days=365)`
2. Public MCP JP Gateway の `counterparty_check` モードで `search_corporations(name="<分析で出た企業名>")`

法人番号 MCP は国税庁の公表データそのものであり、JP Bids MCP と同じ「出典明記・添付資料は保存しない」原則で動く読み取り専用サーバーである。両者を並べても、増えるのは判断材料であって、増えるリスクではない。

### シナリオ3: 入札 × チーム共有 — 保存検索・ICS・Slackメモで営業チームに配る

営業担当が一人で入札を見つけて、一人で締切を覚えている状態は、担当者が休むと止まる。`save_search` / `check_saved_search` / `list_saved_searches` で条件を保存しておけば、新着案件が出たときに同じ条件で再確認できる。見つけた案件は、今回追加した ICS ダウンロードでチームのGoogleカレンダーに、Markdownメモのダウンロードで検討経緯をそのままSlackへ貼り付けられる。

```
「鹿児島県 IT 役務」の検索条件を保存してください。
新着があれば、締切をICSでカレンダーに追加できる形にしてください。
```

1. `save_search(name="鹿児島IT案件", query="IT", prefecture="鹿児島県", category="役務")`
2. （後日）`check_saved_search(name="鹿児島IT案件")` で新着確認
3. 対応クライアントでは `search_bids_app` の「📅 締切ICS」「📝 メモ保存」ボタンでその場でファイル化

一人の担当者の頭の中にあった「あの案件、締切いつだったか」が、チーム全員が見られるカレンダーとメモに変わる。これは新しい入札情報を作っているわけではない。同じ公的データを、担当者が休んでも止まらない形に変えているだけだ。

## 公式仕様から外れない理由

三つのシナリオはどれも、JP Bids MCP 単体を肥大化させずに成立している。理由は単純で、`analyze_past_awards` や `save_search` のようなツールは「入札」というドメインの中に留め、法人番号・補助金・会計・チャットは、それぞれ別の MCP サーバーとして並べているからだ。

MCP の `readOnlyHint` や `destructiveHint` のようなアノテーションは、ヒントであって強制ではない。安全性は、認証範囲・アクセス制御・保存方針そのものから来る。JP Bids MCP が守っているのは、出典を必ず返すこと、添付資料は URI のみでダウンロードして保存しないこと、そして KKJ への短時間大量アクセスを避けることだ。三つの連携シナリオも、この境界の中で動く。

## まとめ — 「載っている」ことと「壊れない」ことの距離

ディレクトリに載ることは、入り口が見つかることにすぎない。商談の前に検索して、意味の取れないエラーに一度当たれば、その入り口はもう使われなくなる。

今回直したのは、エラーメッセージの文面と、ダウンロードボタンの数だけだ。地味な変更に見える。しかし、これが積み重なった先にあるのは、入札を探す人が、補助金と会計と法人番号とチームの予定表まで、同じ会話の中で扱える状態である。

公的な事実は、ただのデータではない。制度が外に出した、最小単位の約束である。JP Bids MCP がその約束を壊さずに運べているかどうかは、派手な機能ではなく、502が出たときに何が表示されるかで測られる。
