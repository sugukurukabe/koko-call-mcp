# ADR-0023: Kesiapan Migrasi MCP 2026-07-28

## Status / Status / Status

Accepted / Accepted / Diterima

## Context / 背景 / Konteks

MCP `2026-07-28` is the largest protocol revision since launch. It makes the protocol stateless, removes `initialize` / `initialized` and `Mcp-Session-Id`, introduces `Mcp-Method` / `Mcp-Name` routing headers, moves Tasks to an extension, hardens OAuth, and deprecates Roots, Sampling, and Logging.

JP Bids MCP and Public MCP JP Gateway are already close to the target shape because both HTTP transports use `sessionIdGenerator: undefined`. However, both servers previously accepted only `2025-11-25`, did not validate the new routing headers, and the Gateway had started to expose MCP Logging even though the RC marks Logging as deprecated.

## Decision / 決定 / Keputusan

- Accept both `2025-11-25` and `2026-07-28` protocol versions during the transition window.
- Validate `Mcp-Method` and `Mcp-Name` when clients send them. If headers disagree with the JSON-RPC body, reject with `400`.
- Keep the HTTP transport stateless. Do not introduce sticky sessions or a shared protocol-level session store.
- Add `iss` to JP Bids OAuth authorization responses and issued JWTs to prepare for RFC 9207 validation.
- Treat Gateway MCP Logging as transitional compatibility only. Operational observability is `/metrics`, audit buffer, stderr, and future OpenTelemetry.
- Do not implement the Tasks extension until a workflow truly needs durable long-running execution and host support is clearer.
- Keep API surface compatibility: no published tool name, required input, or existing output field is removed.

## Consequences / 影響 / Konsekuensi

Positive:

- Clients can begin testing `2026-07-28` requests before the final spec date.
- Load balancers and gateways can route on headers without parsing JSON bodies when clients send them.
- Existing clients using `2025-11-25` keep working.
- OAuth mix-up mitigation improves without changing client-visible scopes.

Trade-offs:

- Full `server/discover`, `ttlMs` / `cacheScope`, and MRTR support still depend on SDK support.
- Supporting both protocol dates temporarily increases contract test coverage needs.
- `Mcp-Name` is meaningful mainly for named methods such as `tools/call`; generic JSON-RPC methods may omit it.
